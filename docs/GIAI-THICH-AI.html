1. Tổng quan — AI này là gì, làm gì?

Đây không phải một con chatbot đơn lẻ. Nó là một hệ thống đa tác tử (multi-agent system): nhiều "nhân viên AI" nhỏ, mỗi người giỏi một việc, phối hợp với nhau để phục vụ khách mua quần áo.

Hệ thống có 4 agent, mỗi agent chạy như một dịch vụ (server) riêng biệt:

AgentCổngVai tròVí dụ câu hỏi xử lý
Orchestrator 8000 Bộ não điều phối. Nhận câu hỏi của khách, quyết định giao việc cho ai. Mọi câu hỏi đều vào đây trước
Search Agent 8001 Tìm sản phẩm trong kho bằng tìm kiếm ngữ nghĩa (vector search). "Tìm áo khoác đen cho tôi"
Stylist Agent 8002 Stylist AI — tư vấn phối đồ thành bộ outfit hoàn chỉnh. "Phối đồ đi phỏng vấn cho tôi"
Order Agent 8003 Xử lý giỏ hàng, tạo đơn, sinh link thanh toán VNPay. "Thêm áo này vào giỏ", "Thanh toán"
Cách hình dung dễ nhất: Orchestrator giống quản lý cửa hàng. Khách hỏi gì, quản lý nghe xong rồi gọi đúng nhân viên: nhân viên kho (Search), stylist (Stylist), hoặc thu ngân (Order). Quản lý không tự trả lời — luôn giao việc cho chuyên viên.

Các công nghệ chính

  • FastAPI — framework web để mỗi agent chạy thành 1 server HTTP.
  • OpenAI (LLM) + Function Calling — "bộ não" suy luận; LLM tự quyết định gọi "công cụ" (tool) nào.
  • Google A2A SDK (Agent-to-Agent) — giao thức chuẩn để các agent "nói chuyện" với nhau qua HTTP.
  • Backend Spring Boot (cổng 9000) — nơi chứa dữ liệu thật: sản phẩm, giỏ hàng, đơn hàng.

2. Luồng xử lý 1 câu hỏi (end-to-end)

Ví dụ khách gõ: "Tìm áo sơ mi trắng và thêm vào giỏ". Đây là hành trình câu hỏi đi qua hệ thống:

Điểm quan trọng: mỗi agent (cả orchestrator lẫn worker) đều có một "vòng lặp ReAct" riêng. Tức là bên trong Search Agent cũng có một LLM khác tự suy nghĩ và gọi tool. Nên hệ thống thực chất là "LLM gọi LLM" nhiều tầng.

3. Bốn khái niệm AI cốt lõi cần hiểu trước

① LLM & Function Calling (gọi hàm)

LLM (như GPT) bình thường chỉ sinh ra chữ. "Function calling" cho phép ta đưa cho LLM một danh sách công cụ (mỗi công cụ có tên + mô tả + tham số). LLM đọc câu hỏi, nếu thấy cần dùng công cụ, nó trả về "hãy gọi hàm search_products với query='áo trắng'". Code của ta thực thi hàm đó rồi đưa kết quả lại cho LLM.

② Vòng lặp ReAct (Reason + Act = Suy luận + Hành động)

Đây là pattern AI then chốt của cả dự án. Thay vì LLM trả lời 1 phát, nó lặp:

Nghĩ (Reason) → Gọi tool (Act) → Quan sát kết quả (Observe) → Nghĩ tiếp... ↑________________________ lặp lại tối đa 8 lần ________________________↓ → Khi đủ thông tin: trả lời cuối cùng

Nhờ vậy AI có thể: tìm sản phẩm → thấy ID → dùng ID đó để thêm vào giỏ → xác nhận.

③ Kiến trúc Skill (kỹ năng)

Trong dự án này: Agent = một cái hộp chứa các Skill. Mỗi Skill là một năng lực cụ thể, gồm 3 thứ: (a) các tool mà LLM được phép gọi, (b) hàm thực thi tool, (c) đoạn prompt hướng dẫn LLM cách dùng skill này.

④ Giao thức A2A (Agent-to-Agent)

Mỗi agent công bố một "Agent Card" (danh thiếp) tại địa chỉ /.well-known/agent.json, ghi rõ "tôi tên gì, làm được gì". Orchestrator lúc khởi động sẽ quét các danh thiếp này để biết có những agent nào, rồi gửi việc cho chúng qua tin nhắn chuẩn A2A.

39@dataclass
40class ToolResult:
49    content: str | dict | list   # trả về cho LLM "đọc"

ToolResult = kết quả khi chạy 1 tool. Tách làm 2 phần rất quan trọng:
  • content: phần văn bản/JSON đưa ngược lại cho LLM để nó "quan sát" và suy luận tiếp.
  • data: dữ liệu thô có cấu trúc (vd: danh sách sản phẩm, đơn hàng) — gửi thẳng cho giao diện hiển thị, không bắt LLM xử lý lại. Tách 2 luồng này giúp giao diện hiện đúng thẻ sản phẩm.
53class Skill(ABC):                       # lớp trừu tượng — bắt buộc lớp con cài đặt
63    @property
64    @abstractmethod
65    def id(self) -> str: ...        # mã skill (vd "product-search")
68    def name(self) -> str: ...      # tên hiển thị
72    def description(self): ...      # mô tả — agent khác đọc để biết nên gọi không
85    @abstractmethod
86    def get_tools(self) -> list[ToolDefinition]: ...
90    @abstractmethod
91    async def execute_tool(self, tool_name, args) -> ToolResult: ...
97    @abstractmethod
98    def get_prompt_instructions(self) -> str: ...
Skill là một "hợp đồng" (ABC = Abstract Base Class). Bất kỳ skill cụ thể nào (Search, Order, Stylist...) bắt buộc phải cài đặt đủ:
  • id / name / description — thông tin nhận dạng (đưa lên Agent Card).
  • get_tools() — khai báo danh sách tool LLM được dùng.
  • execute_tool() — code thật chạy khi LLM gọi tool. (async = chạy bất đồng bộ, không chặn.)
  • get_prompt_instructions() — đoạn hướng dẫn nhét vào system prompt.
Đây chính là "khuôn". Nhờ có khuôn này, thêm một agent mới chỉ là viết một class Skill mới.

7. Các Prompt — "linh hồn" điều khiển LLM

Hành vi AI không nằm hết trong code Python — phần lớn nằm trong các file .yaml ở thư mục prompts/. Đây là nơi "dạy" LLM cách cư xử. Sửa prompt = đổi hành vi AI mà không cần đụng code.

8. ⚠️ Bug & điểm cần lưu ý (đã kiểm tra kỹ)

Trong quá trình đọc source, tôi phát hiện các điểm sau cần bạn lưu tâm:

🔴 Bug 1 — context không tồn tại trong Order Agent

File: services/order/skills/order_processing.py, hàm execute_tool() (dòng 159).
Vấn đề: chữ ký hàm là execute_tool(self, tool_name, args) — không có tham số context. Nhưng nhánh add_to_cart (dòng 168) và add_multiple_to_cart (dòng 197) viết:
user_id = context.get("user_id") or args.get("user_id")
Hậu quả: Python ném NameError: name 'context' is not defined ngay khi khách thêm sản phẩm vào giỏ. Tính năng giỏ hàng qua AI sẽ lỗi.
Cách sửa gợi ý: bỏ context.get("user_id") or, chỉ dùng args.get("user_id"); và đảm bảo user_id được nhồi vào args (hiện user_id đang nằm trong text dạng [user_id=X], cần regex bóc ra như order-processing.yaml hướng dẫn LLM làm).

🟠 Bug 2 — LLM Planning gần như không bao giờ chạy

File: services/orchestrator/main.py (dòng 72-76) + planning_agent.py (dòng 105-108).
Vấn đề: PlanningAgent.__init__ đặt self._use_llm = openai_client is not None. main.py gọi PlanningAgent(openai_client=None, ...) → _use_llm = False. Sau đó main.py gán planning_agent._openai = AsyncOpenAI(...) nhưng không bật lại _use_llm.
Hậu quả: trong create_plan(), nhánh if self._use_llm: (dòng 160) luôn False → khi regex không khớp, kế hoạch luôn rơi về mặc định "1 bước Search Agent" thay vì để LLM lập kế hoạch linh hoạt.
Cách sửa gợi ý: trong main.py thêm planning_agent._use_llm = True sau khi gán _openai; hoặc truyền thẳng client vào constructor.

🟡 Lưu ý 3 — Định tuyến bị gọi LLM 2 lần

File: tools/route_tool.py → routing_agent.py.
LLM của orchestrator chọn tool route_to_agent và đã chỉ định agent_name. Nhưng execute_route_to_agent() lại gọi routing_agent.run() — vốn chạy nguyên một vòng lặp LLM tool-calling nữa để... chọn agent lần thứ hai. Tham số agent_name mà orchestrator chọn gần như bị bỏ qua (chỉ dùng làm nhãn hiển thị). → Tốn thêm 1 lượt gọi LLM không cần thiết. Không gây sai kết quả, nhưng chậm hơn và tốn tiền hơn.

🟡 Lưu ý 4 — Bộ nhớ chỉ nằm trong RAM

MemoryStore và SmartConversationManager lưu toàn bộ trong RAM. Restart server = mất hết lịch sử hội thoại. Ngoài ra nếu chạy nhiều bản orchestrator (scale ngang/load balancer) thì mỗi bản có bộ nhớ riêng → khách bị "quên" ngẫu nhiên. Production nên chuyển sang Redis hoặc database.

🟡 Lưu ý 5 — add_to_cart nuốt lỗi nhưng vẫn báo thành công

File: order_processing.py dòng 186-192. Khi gọi backend lỗi, code chỉ ghi log rồi vẫn trả {"status": "added"} — kèm chú thích "Still return success to user". Khách sẽ thấy "đã thêm vào giỏ" trong khi backend chưa thật sự thêm. Nên trả lỗi rõ ràng để khách biết.

🟢 Điểm tốt đáng ghi nhận

  • Kiến trúc nhất quán: cả 4 agent dùng chung khung Skill/Agent/Executor — dễ đọc, dễ mở rộng.
  • Nhiều lớp dự phòng (fallback): LLM lỗi → keyword routing; LLM lười gọi tool → direct fallback; regex trước, LLM sau. Hệ thống khó "chết hẳn".
  • Chống hallucination: mọi prompt đều ép "luôn dùng tool, đừng bịa".
  • Tách content / data: LLM xử lý chữ, frontend nhận dữ liệu thô — sạch sẽ.
  • Tiết kiệm chi phí: ưu tiên regex/keyword trước khi gọi LLM; cửa sổ trượt giới hạn token.
  • Prompt tách ra file YAML: chỉnh hành vi AI không cần sửa code.

📌 Tóm tắt 1 dòng

Đây là một hệ thống multi-agent thiết kế bài bản theo pattern ReAct + Function Calling + giao thức A2A: một orchestrator điều phối 3 worker agent (Search/Stylist/Order), mỗi agent tự chạy vòng lặp suy luận–gọi tool riêng. Kiến trúc tốt, có nhiều lớp dự phòng, nhưng cần sửa Bug 1 (lỗi context trong giỏ hàng) và Bug 2 (LLM planning bị tắt) trước khi đưa vào dùng thật.
